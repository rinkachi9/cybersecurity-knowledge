## What it is?

**SLSA (Supply-chain Levels for Software Artifacts)** is a **security framework for software supply chain integrity**, designed to prevent, detect, and mitigate **software supply chain attacks**.

SLSA was originally developed at Google and is now maintained by the **Open Source Security Foundation (OpenSSF)**.

> Core mission:
>
> Ensure that
>
> what you build is exactly what you intended to build
>
> , and that it has
>
> not been tampered with at any stage
>
> of the software supply chain.

SLSA addresses risks across:

- Source code
- Build systems
- CI/CD pipelines
- Dependencies
- Artifacts and provenance
- Release and distribution

## Importance

Modern software is **assembled**, not written:

- 70-90% of code is third-party
- CI/CD pipelines are high-value targets
- Build systems often run with excessive privileges
- Artifacts are rarely verifiable end-to-end

### High-profile attack classes SLSA addresses:

- Dependency confusion
- Build system compromise
- CI pipeline injection
- Malicious maintainers
- Artifact substitution
- Provenance forgery

SLSA was created to **systematically close these attack paths**.

## SLSA Design Philosophy

SLSA is built on several non-negotiable principles:

### End-to-End Trust

Security must extend from:

**Source → Build → Artifact → Distribution**

#### Verifiability Over Trust

You should **verify**:

- Who built the artifact
- How it was built
- From which sources
- Using which build steps

#### Automation by Default

Manual processes **cannot scale** and **cannot be trusted**.

#### Incremental Adoption

SLSA supports gradual maturity increases without re-architecting everything.

### Core concept

#### SLSA IS:

- A **framework**
- A **maturity model**
- A **set of technical requirements**
- A **shared language for supply chain security**

#### SLSA IS NOT:

- A compliance standard
- A tool
- A checklist
- A replacement for secure coding

## Core components

SLSA defines security requirements across **four core dimensions**:

1. **Source**
2. **Build**
3. **Provenance**
4. **Dependencies**

These are evaluated across **four SLSA Levels**.

## SLSA levels

Overview of SLSA Levels

| Level | Security Goal |
| --- | --- |
| **SLSA 1** | Basic build process visibility |
| **SLSA 2** | Tamper-resistant provenance |
| **SLSA 3** | Hardened, isolated builds |
| **SLSA 4** | Hermetic, reproducible, verified builds |

Each level builds on the previous one.

### SLSA Level 1 - Build Process Visibility

#### Goal

Ensure the build process exists and is documented.

#### Key Requirements

- Scripted / automated build
- Build process defined as code
- Artifact is produced deterministically from the pipeline

#### Threats Addressed

- Undocumented manual builds
- Unknown build steps

#### Typical Implementation

- CI pipeline (GitHub Actions, GitLab CI, Azure Pipelines)
- No strong integrity guarantees yet

> Level 1 = Awareness, not security

### SLSA Level 2 - Tamper-Resistant Provenance

#### Goal

Ensure that build provenance is **authentic and cannot be forged**.

#### Key Requirements

- Build provenance is generated automatically
- Provenance is cryptographically signed
- Provenance is stored immutably
- Build runs on trusted infrastructure

#### Threats Addressed

- Artifact substitution
- Fake build metadata
- Shadow pipelines

#### Core Concept: Provenance

**Provenance includes:**

- Source repository
- Commit hash
- Build system identity
- Build steps
- Dependencies (partial)

This is the **heart of SLSA**.

### SLSA Level 3 - Hardened & Isolated Builds

#### Goal

Prevent **build system compromise**.

#### Key Requirements

- Isolated, ephemeral build environments
- Strong access control
- No manual intervention
- Source and dependencies are immutable during build
- Provenance is generated by the build platform (not scripts)

#### Threats Addressed

- CI runner compromise
- Credential reuse
- Lateral movement inside CI
- Pipeline injection

#### Typical Controls

- Ephemeral CI runners
- OIDC-based identity
- No long-lived secrets
- Least privilege IAM

### SLSA Level 4 - Hermetic & Reproducible Builds

#### Goal

Provide **maximum assurance** against even insider threats.

#### Key Requirements

- Hermetic builds (no network access)
- Fully pinned dependencies
- Reproducible builds
- Independent verification possible

#### Threats Addressed

- Malicious maintainers
- Covert dependency injection
- Build-time data exfiltration

#### Reality Check

SLSA 4 is:

- Extremely difficult
- Expensive
- Rare in real-world enterprises

Typically reserved for:

- Critical infrastructure
- Cryptography
- OS distributions
- National security software

## Provenance - central pillar

**What Provenance Solves**

Without provenance:

- You cannot trust artifacts
- You cannot investigate incidents
- You cannot verify releases

**Provenance Enables:**

- Artifact verification
- Policy enforcement
- Forensics
- Zero-trust pipelines

**Common Formats**

- in-toto attestations
- JSON-based, cryptographically signed metadata

## SLSA and DevSecOps

SLSA fits **natively** into DevSecOps.

| DevSecOps Area | SLSA Impact |
| --- | --- |
| CI/CD | Hardened pipelines |
| IAM | Identity-based builds |
| Secrets | Elimination of long-lived secrets |
| IaC | Policy-driven enforcement |
| Observability | Traceability of releases |

SLSA is **DevSecOps maturity expressed as supply chain guarantees**.

## SLSA and Zero Trust

SLSA is **Zero Trust for software artifacts**:

- Never trust build outputs implicitly
- Verify provenance every time
- Enforce policies at deploy time
- Assume pipeline compromise is possible

## SLSA vs Related Frameworks

| Framework | Focus |
| --- | --- |
| NIST CSF | Enterprise risk |
| SANS | Operational skills |
| OWASP | Application risks |
| SBOM | Dependency visibility |
| **SLSA** | **Build & artifact integrity** |

SLSA **complements**, not replaces, these frameworks.

## Common implementation pitfalls

- Treating SLSA as documentation only
- Generating provenance without verification
- Using long-lived CI secrets
- Ignoring dependency integrity
- Assuming cloud CI is “secure by default”

## Skills required

A professional implementing SLSA must understand:

- CI/CD internals
- IAM & workload identity
- Cryptographic signing
- Supply chain attack techniques
- Artifact registries
- Policy engines (OPA, admission controllers)
- Cloud-native security

This is **senior-level DevSecOps security**.

## Strategic value

SLSA enables:

- Trustworthy releases
- Faster incident response
- Regulatory readiness
- Secure open-source consumption
- Defense against modern supply chain attacks

It transforms:

> “We think this artifact is safe”
>
> into
>
> “We can
>
> prove
>
> this artifact is safe.”

## Summary

SLSA is one of the **most important modern cybersecurity frameworks**.

It addresses the **single most exploited attack surface today**: the **software supply chain**.

If:

- **NIST CSF** defines *why security matters*
- **SANS** teaches *how to defend*
- **Mandiant** shows *how attackers really operate*

Then:

> SLSA defines how to ensure software integrity in a zero-trust world.
